# Codex 可用性实测（Batch4 复核前置）

- 时间：2026-11-19 15:27–15:36
- 机器：Windows DESKTOP-C1V00J3
- CLI：`C:\Users\longf\Tools\codex\codex.cmd`，codex-cli 0.169.0
- 模型：`nvidia/nemotron-3-ultra-550b-a55b`（provider `nvidia`，`https://integrate.api.nvidia.com/v1`）
- 目的：判断 Codex 现在能否开工分担 Batch4 独立复核

## 一、三组探针与结果

| 探针 | 内容 | 是否读文件 | 结果 | 耗时 | tokens used |
| --- | --- | --- | --- | --- | --- |
| P1 | 让它写 `out1.txt` 一行字 | 否 | **成功**，自主执行 `echo`、回读、汇报 | 约 10s | 17,006 |
| P2 | 让它读 `scheduler.py` 再做评审 | **是** | **失败**：读完第一个文件后第二次请求 `429 Too Many Requests`，重试耗尽，无产出 | 约 16s | 6,857 |
| P3 | 代码直接内联进 prompt，禁止读写文件，单次作答 | 否 | **成功**，输出「未发现问题」 | 约 130s | 19,084 |

## 二、结论（这是本轮最重要的判断）

1. **Codex 是活的，能真干活。** P1 它不是"说要做"，是实际调起 `pwsh -Command 'echo PONG-2026 > out1.txt'` 写文件、再 `cat` 回读确认，然后才汇报。工具链、沙箱、shell 都通。
2. **限流卡在「请求次数」，不是「token 总量」。** P1 烧 17k tokens 一次过；P2 只烧 6.8k 却挂——差别在于 P2 要"读文件"这个动作额外发了一次请求。也就是说：**只要模型决定调用工具（读文件 / 跑命令 / 再想一轮），就要付一次请求配额，而配额约等于每分钟 1 次。**
3. **因此 Codex 不能自主读代码库。** 想让它评审 Batch4，它必须先读文件——这一步就 429。四批复核一直欠着，根因不是模型不行，是**用法不对**。
4. **正确用法：代码内联 + 单次作答。** P3 证明这条路通：把待评审代码整段塞进 prompt，禁止它读写任何文件，它可以给出结论。但代价是**慢（约 2 分钟/次）**，且 prompt 要控制在能一次消化的体量。

## 三、能力边界（按实测划，不按猜测划）

| 能力 | 判定 | 依据 |
| --- | --- | --- |
| 自主执行命令并自验 | 可用（小任务） | P1 |
| 自主读多文件做评审 | **不可用** | P2 429 |
| 内联代码单点评审 | 可用，但约 2 分钟/次 | P3 |
| 作为主开发写多文件代码 | **不可用**（要读要写要多轮） | 推论：每次工具调用都撞配额 |
| 独立跑验收脚本 | 未测，按 P2 规律预计不可用（跑命令=额外请求后可，但读输出再判断=再一轮） | — |

## 四、对分工的影响（需要拍板）

现状是「我落地 + Codex 复核」，但复核这一环此前从未真正跑起来。现在可以跑，但只能跑成**"我把代码贴给它、它吐一条意见"**的形式：

- 能提供的价值：一个不受我思路污染的独立视角，尤其在判定语义、边界条件上挑刺。
- 不能提供的价值：它看不到整个工程、不能跑测试、不能验证自己说的话。**所以它的意见只能当参考，不能当验收依据。**

P3 这次它答「未发现问题」。我自己复看 `scheduler.py`，至少能指出两处它漏了：
1. 熔断计数用的是「该 trace 历史累计失败任务数」，不是「连续失败」，口径命名与实现不符（实现按阈值语义无害，但命名会误导后续维护）。
2. 每轮扫描都用 `list_tasks_by_status("执行失败")` 全量捞失败任务来推 trace 集合，台账增长后是 O(n) 扫描，应改为按 trace 聚合或维护失败计数。

这两条不影响 Batch4 判定正确性（44 条断言仍全绿），属可改进项。但它"未发现问题"说明：**单次内联评审的召回率有限，不能当作唯一把关。**

## 五、建议

**方案 A（推荐，零成本）**：Codex 定位为"单点挑刺器"。每批收口时，我把该批核心判定代码内联成一份 prompt 发它，拿一条独立意见归档进验收单，注明"仅供参考"。不指望它当守门员。
**方案 B**：升级 NIM 配额或换 provider（如自备 OpenAI key / 换 Azure），让它能自主读代码库、跑脚本。那时才谈得上"Codex 主开发 + 交叉复核"。
**方案 C**：Mac 端 Codex 也按 P3 方式试一次，看两端是否同一表现（Mac 是 0.142 alpha，同 provider，预计同病）。

下一步 Batch5（极简前端）不受此影响，可以按 A 继续推进。
