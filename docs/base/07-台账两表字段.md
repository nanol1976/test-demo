# 07 · 台账两表字段

## 铁律（先看这条）

**只追加与状态更新，禁止删除与覆盖。**
- 不出现 `.delete()`、不出现 `DROP TABLE`、不出现 truncate（验收脚本会扫）
- 仓储层不提供任何 delete 方法（连"方便一下"的都不留）
- 要"撤销"，只能追加一条新报文把状态改回去，历史留在 JSONL

## 表一：`pipeline_ledger`（流水线）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `trace_id` | str PK | 一条需求一个，全程不改 |
| `original_demand` | text | 原始需求原文（人怎么说的就怎么记） |
| `overall_status` | str | 5 值：pending/running/success/aborted/failed（CHECK 约束） |
| `start_time` | datetime | 带时区 |
| `end_time` | datetime? | 终态时写 |
| `pause_flag` | bool | 暂停标记，默认 False |
| `archive_path` | str? | JSONL 落盘路径 |

> 台账只增不删：加字段走迁移（见 13-迁移规范），**不做物理删除**。`last_heartbeat_time` 就是 v004 加列的例子。

## 表二：`task_ledger`（任务）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `task_id` | str PK | 1..64 |
| `trace_id` | str FK索引 | 必须属于某条流水线 |
| `target_worker` | str | 派给谁 |
| `task_goal` | text | 干什么，非空（`min_length=1`） |
| `acceptance_criteria` | json list? | 验收标准，`Optional[List[str]]` |
| `depends_on` | json list | 依赖的 task_id 列表（`mapped_column(default=list)`，**不改 default_factory**） |
| `status` | str | 7 个中文值（CHECK 约束），默认 `待拆解` |
| `is_high_risk` | bool | 高危标记 |
| `dispatch_time` | datetime? | 超时判定起算点 |
| `return_time` | datetime? | 回传时间 |
| `last_heartbeat_time` | datetime? | **Batch12** 最近一次心跳时间（v004 新增，可空）。只由 `task_heartbeat` 更新，**不改状态**；看板"执行方在线视图"靠它聚合 |
| `max_retry` / `remaining_retry` | int | 重试上限 / 剩余；扣到 0 不为负 |
| `reject_reason` | text? | 驳回原因 |
| `abort_reason` | text? | 中止/超时/心跳告警原因（前缀约定见下） |

## 表三：`message_archive`（报文索引）

| 字段 | 说明 |
| --- | --- |
| `archive_id` | 自增主键 |
| `trace_id` / `task_id` / `msg_type` / `sender` / `timestamp` | 幂等键 + 追溯 |
| 唯一约束 | `uq_archive_message(trace_id, task_id, msg_type, timestamp)` |

正文存 JSONL（`archive/{trace_id}/{date}.jsonl`），索引存表。**先写正文再写索引**；撞唯一约束则回退查已有记录返回。

## abort_reason 前缀约定

| 前缀 | 谁写 | 含义 |
| --- | --- | --- |
| `[超时]` | 平台 | 调度后超 `task_timeout_seconds` 未回传，**已置执行失败** |
| `[心跳告警]` | 平台 | 超 `heartbeat_timeout_seconds` 无心跳，**仅告警不改状态** |

两个前缀同时也是幂等标记：已有 `[心跳告警]` 前缀的不会重复写。

## 归档目录

`{ARCHIVE_ROOT}/{trace_id}/{YYYY-MM-DD}.jsonl`，日期按 **UTC** 取（避免跨时区部署出现"昨天的文件"）。

## 三条数据卫生要求

1. `init_db.py` **不写任何测试数据**（早期版本硬写测试数据，已清理）。
2. 验收脚本各用各的库（`data/verify_bN.db`）与归档目录（`archive/_verify_bN`），跑前清干净——否则会撞"上轮残留导致行数翻倍"（Batch2 踩过）。
3. 时间统一 aware+UTC 存储；从 SQLite 取回的 naive 时间用 `ensure_utc` 统一按 UTC 解释，否则 aware-naive 相减抛 TypeError。

## 附：运行态注册表 `worker_registry`（非台账，可重建但一行不丢）

| 列 | 说明 |
| --- | --- |
| `worker_id` + `instance_id` | 复合主键（Batch14） |
| `concurrency` | Worker **自报**的当前上限 |
| `concurrency_limit`（API 字段 `limit`） | Worker 自报的当前实际并发（物理列名避开 SQL 关键字 `limit`） |
| `desired_limit` | 平台**下发**的期望上限（Batch15）；0 = 未下发。与 `concurrency` 分开，才能看出"下发了但没生效" |
| `in_flight` / `handled` / `status` / `last_seen` / `meta` | 运行态观测，不参与台账判定 |

## 附2：运维审计表 `worker_quota_audit`（append-only）

| 列 | 说明 |
| --- | --- |
| `worker_id` + `instance_id` | 下发目标 |
| `desired_limit` | 改完后的期望上限 |
| `prev_limit` | 改之前的值（0 = 之前没下发过） |
| `command` | 固定 `master:worker-limit`（将来别的运维指令也落这张表） |
| `reason` | 人写的原因，可为空 |
| `created_at` | 落库时间 |

铁律：**只追加，不更新不删除**。这张表记的是"谁动了运维参数"，跟业务台账一样要能倒查。
