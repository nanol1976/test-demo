# 13 · 迁移规范

数据库结构的每一次变化，都必须走**版本化迁移**，不许"改模型然后靠启动自检兜底"。

## 一、为什么是自研 runner，不是 Alembic

| 维度 | Alembic | 本平台 runner |
| --- | --- | --- |
| 安装面 | alembic + Mako + markupSafe（镜像限流时直接挂） | 零新增依赖（`sqlalchemy` 已在） |
| 配置面 | `alembic.ini` + `env.py` + 三处路径替换 | 一个目录 + 一个约定 |
| 适用规模 | 多分支、多人并行、需要 autogenerate | 单库、单线、无分支、无 merge |
| 迁移量级 | 大 | 当前 2 个版本，预期长期保持在个位数 |

结论：**当前规模下 Alembic 换来的是维护面，不是能力。** 但 `schema_version` 表本身就是 Alembic 认的版本锚点，真要迁移过去时按版本号一一对应即可。

## 二、目录与约定

```
migrations/
├── __init__.py
├── runner.py                # 发现 / 校验 / 执行 / 幂等
└── versions/
    ├── v001_baseline.py     # 基线三表
    └── v002_archive_msg_type_index.py
```

每个迁移文件必须导出三个东西：

```python
VERSION = 2                                     # 必须与文件名 vNNN 的 NNN 一致
NOTE = "message_archive.msg_type 加索引"          # 一句话，会写进 schema_version.note
def up(conn):                                   # 接收 SQLAlchemy Connection
    ...
```

- `NNN` 三位数字，**唯一且递增**；重号会被 runner 直接拒绝。
- `up(conn)` 在调用方的事务里跑：**抛异常就回滚**，版本号不会落库。
- 可选的 `down(conn)` 只是书面参考——**本框架不自动回滚**（理由见第五节）。
- 不符合 `vNNN_xxx.py` 命名的文件（如 `__init__.py`）不参与。

## 三、新增一次迁移的标准动作

1. 在 `migrations/versions/` 建 `vNNN_说明.py`，`NNN` = 当前最大版本 + 1。
2. 写 `VERSION` / `NOTE` / `up(conn)`。**`up` 必须可重复执行**（用 `IF NOT EXISTS` 或先 inspect 再建）。
3. 本地跑三连：`--check`（应不通过）→ 执行（应通过）→ `--check`（应通过）。
4. 在 `scripts/verify_b7.py` 里补断言（结构变化必须被断言覆盖）。
5. 跑 `python scripts/ci.py`（含迁移门禁三段式）。
6. 双端跑一遍，写进验收单。

## 四、命令

```bash
python deploy/migrate.py                      # 升级到最新
python deploy/migrate.py --check              # 只检查（上线前预检；不通过 exit 1）
python deploy/migrate.py --status             # 列出每个版本：已应用 / 待应用
python deploy/migrate.py --to 2               # 只升到 v002（分段上线用）
python deploy/migrate.py --dry-run            # 只打印将要执行什么
python deploy/migrate.py --baseline 2         # 接管既有库：表已建好、只补版本记录
python deploy/migrate.py --baseline 2 --force # 已有版本记录时强制重写（慎用）
```

### `--baseline` 是干什么的

有一类库进不了迁移体系：**表是手工建好的、或从更早的非迁移版本恢复过来的，结构已经正确，但没有 `schema_version` 记录**。这种库直接跑 v001 会重复建表报错。

`--baseline N` 就是"认账"：只在 `schema_version` 里写入 1..N 的版本记录，**一个 `up()` 都不执行**。接管之后，后续新迁移从 N+1 继续。

四道闸门，缺一不可：

| 闸门 | 行为 |
| --- | --- |
| 版本范围 | 必须 `1..latest`，否则 exit 1 |
| 表完整性 | 期望表缺任何一张就拒绝（"baseline 只用于表已建好的库，缺表请直接跑迁移"） |
| 已有版本记录 | 默认拒绝；确需覆盖才加 `--force` |
| 留痕 | 每条 note 写 `baseline 接管：{原 note}（未实际执行）`，事后能看出这不是真跑过 |

`--force` 会 `DELETE FROM schema_version`（**只有这张元数据表**，台账三表一行都不碰），然后重写版本记录。这是本平台唯一允许的删除动作，且必须人工显式加参数。

接管后务必立刻跑一次 `--check`，确认库结构与版本号真的对得上。


输出约定（`deploy/run.ps1` / `run.sh` 依赖这几行做日志）：

```
数据库：sqlite:///./data/mvp.db
期望表：['message_archive', 'pipeline_ledger', 'task_ledger']
现有表：[...]
schema_version：0（目标 2）
→ 应用 v001：基线三表：...
→ 应用 v002：message_archive.msg_type 加索引 ...
schema_version：0 → 2
迁移完成，缺表：无
```

## 五、回滚立场

- **代码可以回滚**（`git reset --hard batchN`），**数据不自动回滚**。
- 台账铁律是"只追加与状态更新"，`down()` 一律不执行——删列/删表会毁掉历史。
- 真要撤销一次结构性变更：**备份库 → 手写一条新的向前迁移**（例如把索引删掉再建别的），而不是倒回旧版本。
- 上线前先把库和 `archive/` 目录各备一份，这条写进 `11-启动自检清单`。

## 六、CI 门禁

`scripts/ci.py` 的迁移门禁是**三段式**，缺一段都不算过：

1. 空库 `--check` 必须**不通过**（证明预检真的能发现问题，不是永远返回 0）
2. `upgrade` 必须成功
3. 升级后 `--check` 必须**通过**；再跑一次 upgrade 必须幂等（"无待应用迁移"）

## 七、常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 改模型不写迁移 | 老库缺列/缺索引，查询报错 | 必须新增 `vNNN` |
| 迁移里写 `DROP`/`DELETE` | 毁历史数据，违反台账铁律 | 只做加法（加表/列/索引） |
| `up` 里不判存在性 | 重复执行报错，幂等失效 | `IF NOT EXISTS` 或先 inspect |
| 版本号重复 / 与文件名不符 | runner 直接拒绝启动迁移 | 递增且唯一 |
| 迁移里连外部网络 | 离线环境跑不了 | 迁移只碰库 |
| 手改已有库的 `schema_version` | 版本与实际结构不一致 | 用迁移脚本改，或 `--baseline` 正式接管 |
| 对空库用 `--baseline` | 表都没建，没东西可"认账" | 空库一律直接跑迁移 |
