# 岗位与权限（Batch31）

> 这份文档解决一个具体问题：平台上有「执行方」，但执行方只是进程，不是岗位。
> 一个进程叫什么名字、能干什么、谁给它发口令 —— 这三件事必须先定死，才谈得上分工。

## 一、三档口令：把「能看」「能回执」「能下指令」拆成三把钥匙

| 档位 | 环境变量 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| 全权 | `API_TOKEN` | 读全部台账、投全部报文、下发全部 `master:*` 指令 | —— |
| 执行方 | `API_TOKEN_WORKER` | 注册/心跳（`POST /api/workers`）、四类回写报文（`task_heartbeat` / `task_return` / `task_reject` / `task_abort`）、读台账 | 派单、人工确认、汇总报文；任何 `master:*` 指令 |
| 只读 | `API_TOKEN_READONLY` | 读全部台账（手机、外发查看） | 任何写操作 |

三档由服务端判定，前端只做配合（`X-API-Mode` 响应头 → 看板置灰写入口）。**口令交给谁，就等于给了谁这个档位的全部权力**，所以：

- 全权口令只给管理侧（看板、人工运维）；
- 执行方口令发给每一台在编机器，包括质检岗 —— 这就是 Batch31 存在的理由：Batch28 的只读口令永远注册不上来（注册本身是写操作），而全权口令发给质检等于把停机权一起交出去；
- 只读口令给手机和外发。

> 缺口记录：只读口令至今**仍然注册不了**（`POST /api/workers` 会 403）。这不是 bug，是刻意的 —— 执行方要能写，就必须用执行方档，不能拿只读档凑。

## 二、岗位命名：`instance_id` = `角色-主机`

平台的注册表主键是 `(worker_id, instance_id)`，所以同一台机器可以挂多个岗位，只要 `instance_id` 不同。命名规则：

```
<角色>-<主机>      例：qa-mac / ops-mac / dev-win / stock-win
```

- **角色**取自下表，`instance_id` 的第一段就是角色；看板据此显示岗位方章；
- **主机**只是区分同名角色的多台机器，不参与权限判定；
- 不在表里的前缀，看板一律显示为「通用」——**不猜**，猜错的岗位比没有岗位更糟。

### 为什么岗位名不进 `worker_id`

`worker_id` 同时是报文协议的 `sender` 枚举（`master` / `dsh` / `workbuddy` / `codex` / `user`，共 5 个值）。把岗位名塞进 `worker_id`，等于改协议、改归档口径、改历史数据。岗位是编制概念，能从 `instance_id` 稳定推导，就不该污染协议。

## 三、岗位表

| 角色前缀 | 岗位 | 主责 | 默认权限边界 |
| --- | --- | --- | --- |
| `mgmt` | 管理 | 派单、编排、汇总、汇报 | 全权口令（只给看板与人工侧，不发给机器） |
| `ops` | 运维 | 部署、巡检、故障处置 | 执行方口令，全仓库可读可跑 |
| `qa` | 质检 | 验收断言、回归门禁 | 执行方口令，**只允许进入 `scripts/`** |
| `dev` | 开发 | 编码、重构、测试 | 执行方口令，全仓库 |
| `stock` | 证券研究 | 行情与财务数据加工、研报产出 | 执行方口令，数据目录 |
| `doc` | 文档 | 文档处理、格式转换、归档 | 执行方口令，文档目录 |
| `viz` | 视觉 | 图片、视频、排版物料 | 执行方口令，素材目录 |
| `news` | 新媒体 | 平台内容、发布与运营 | 执行方口令，内容目录 |

`qa` 的边界是这一批最重要的设计：**质检岗的凭据和它验的对象不在同一个目录**。它拿执行方口令只能注册和回执，`--allow-root` 又把它锁在 `scripts/` 里 —— 验收权是独立的，不是顺手给的。

## 五、上岗与下岗（Mac）

```bash
# 一次性：把执行方口令填进 ~/.mwp/worker.env（chmod 600，不进 plist、不进 git）
deploy/install-mac-workers.sh                 # 首次会生成模板并退出

# 装载/重装（默认 ops-mac 与 qa-mac）
deploy/install-mac-workers.sh
MWP_INSTANCES="ops-mac dev-mac" deploy/install-mac-workers.sh

# 核对与卸载
deploy/install-mac-workers.sh --status
deploy/install-mac-workers.sh --uninstall
```

`launchd` 的三条保证：登录自启（`RunAtLoad`）、进程退出自动拉起（`KeepAlive`）、停止时给 90 秒优雅收尾（`ExitTimeOut`）。一个岗位一个 plist —— launchd 一个 job 只能管一个进程，所以是循环生成，不手工改。

## 六、验收：为什么改的是 `human_confirm_resp`

首单真派出去才发现：状态枚举里有「验收通过」，但**没有任何报文能写它** —— 报文里只有驳回（`task_reject`），没有通过。任务回传后永远停在「待验收」，六步 SOP 的第 5 步是空的。

补法是让既有报文说完整话（不新增报文类型，8 种是对外契约）：

```json
{"msg_type": "human_confirm_resp", "sender": "master",
 "payload": {"approved": true, "accept_tasks": true, "comment": "12 项自检全过"}}
```

`accept_tasks=true` 时，把该流水线下所有「待验收」任务推到「验收通过」；不带这个字段仍是"只留痕、不推进"（老调用方行为不变）。流水线终态仍由 `task_summary` 的 `pipeline_status` 决定，两件事分开。

## 七、Mac 环境基线（首单踩出来的）

| 事实 | 后果 |
| --- | --- |
| `python3` 在 launchd 里解析到 `/usr/bin/python3` = **3.9.6** | 3.10+ 语法（`X \| None`）运行时就炸；脚本一律加 `from __future__ import annotations` |
| 交互 shell 里那个 3.14 是跑工具自带的解释器 | 别拿它当"这台机器有 3.14"的依据，launchd 环境里看不见它 |
| git 不保证保留可执行位 | plist 必须写 `/bin/bash <启动器>`，不要直接 exec 脚本（否则报 `EX_CONFIG 78` 并进 penalty box 反复重试） |

## 八、派单粒度（Batch31-D 起支持到岗位）

派发报文加一个字段就能指定到具体岗位，**不需要新增接口**：

```json
{"task_dispatch": {"payload": {
  "target_worker": "workbuddy",
  "target_instance": "qa-mac"
}}}
```

四条规则：

| 规则 | 行为 |
| --- | --- |
| `target_instance` 缺省 | 身份族内先到先得（Batch9 以来的老行为，一行代码没动） |
| 指定了岗位 | 只有该岗位能在轮询里看到这条活（`GET /api/tasks?...&instance_id=qa-mac`） |
| 指定了没注册过的岗位 | 派单当场 409「在注册表里从未出现」，不建任务（防错字把活派进虚空） |
| 说不清自己是哪个岗位的请求 | 只看得到「未指定岗位」的活，指定给别人的一律不可见 |

回执里带 `metadata.instance_id`，台账 `done_instance` 才会落值；不带则留空（兼容老 Worker，但事后无法追溯）。若实际执行岗位 ≠ 指定岗位，平台不拒收成果，但会在回执 note 里当场点出差异并写 warning 日志。

查询侧另有 `include_all=true` 供管理视图查看全部（含指定岗位的活），默认关闭。首单那种「靠停掉别的机器来保证活落在指定岗位」的人工清场，已经从机制上不再需要。

## 九、让一台机器临时退出编制（Batch31 实证）

| 平台 | 看着对、其实没停的做法 | 真能停的做法 |
| --- | --- | --- |
| Windows | `Stop-ScheduledTask MW-Worker` | `Disable-ScheduledTask` → 按 `CommandLine` 含 `agent_worker.py` 精确杀进程 → 等过一个触发周期确认进程归 0；恢复用 `Enable` + `Start` |
| Mac | 只 `kill` 进程 | `launchctl bootout gui/$UID com.mwp.worker.<实例>`；恢复 `launchctl bootstrap gui/$UID <plist>` |

`MW-Worker` 的触发器是**每 1 分钟重复、持续 3650 天**，`Stop-ScheduledTask` 只停当前那一个实例，一分钟内它就自己回来。

首单"只留质检岗"就是在这里漏的：Windows 在派单前 14:02:33 已自行复活，抢在 `qa-mac` 之前 5 秒做完了 `t-b31-qa-selftest-2` 并回执成功（`run\worker_done.json` 有记录），`qa-mac` 随后领到同一任务、也跑完了，但 `task_return` 被 409 拒（状态已是「待验收」）。所以**第二单实际是 Windows 执行岗干的，不是质检岗**。

判据只有两条，缺一不可：

1. `Disable` 后等 ≥ 70 秒，进程数必须归 0；
2. 派单后检查该机器的本地 done 记录（`run\worker_done.json` / `run\<实例>_done.json`）**不含**新 `task_id`。

第三单按此执行：Windows 的 `done` 里没有 `t-b31-qa-selftest-3`，`qa-mac` 的 `handled` 才 +1 —— 这才是质检岗亲手跑的。
