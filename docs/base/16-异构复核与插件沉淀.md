# 16 · 异构复核与插件沉淀（B32 设计稿）

> 状态：**设计稿，尚未实现**。本文只写设计与验收方法，代码留到 B32-1 / B32-2 两批动手。
> 缘起：2026-11-21 看到 SoduWork（mdiri-ai/SoduWork，MIT，6.2k star）的思路——"一个 harness 执行、另一个 harness 按验收标准复核、人签收，方法沉淀成插件"。不装它，只借这两条设计进本平台。

## 0. 一句话

把「验收」从**人一句话全通过**改成**规则断言 + 异构复核 + 人签收**三段；把跑通的方法从散落的 `SKILL.md` 改成**带版本、可审核、可授权**的插件包。

## 1. 现状（逐条实测，非推测）

| 事实 | 位置 |
| --- | --- |
| `acceptance_criteria` 已是 `Optional[List[str]]` | `app/schemas/__init__.py:59` |
| 但平台**只搬运不解读**：回执落 `待验收` 就结束 | `app/services/dispatch.py` `handle_task_return` |
| 「验收通过」唯一入口是 `human_confirm_resp` + `accept_tasks=true` | `dispatch.py` `handle_human_confirm_resp` |
| 该入口把**整条流水线所有「待验收」无条件**推到「验收通过」 | `ledger.py` `accept_pending_tasks` |
| 「验收驳回」只能由执行方自己 `task_reject` 触发，扣 `remaining_retry` | `dispatch.py` `handle_task_reject` |
| 判断依据只有回执里的 `self_check` 一句文本（如"脚本正常退出（退出码 0）"） | `archive/20261119/t-win-e2e.jsonl` |

结论：**验收环节机器零发言权**。标准写了没人用，签收靠人拍板，驳回只能自己认错。这是整个"像公司"体系里最薄的一环。

## 2. 边界

**做**：每单都有独立于执行者的判断；判断依据是开工前写下的标准；规则与异构两条都过才可签收；方法可复用、可追版本、可授权。

**不做**：不做插件市场 / 不做跨组织授权 / 不新增协议报文（8 种报文不动）/ 不改 11 条接口路径。

## 3. B32-1：异构复核

### 3.1 数据模型（迁移 v011，加三列）

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `review_of` | String(64) null | 自己是复核单时，指向被复核的 `task_id`；普通单为空 |
| `review_verdict` | String(16) null | 被复核任务的结论：`pass` / `fail` / `unreviewed` |
| `review_items` | Text null | 逐项结论 JSON：`[{"id":"c1","ok":true,"evidence":"...","reason":""}]` |

复核者是谁不再加列——复用 B31-D 的 `done_instance`（复核单回执时照常落它）。

### 3.2 流程

```
派单(带 criteria) → 执行 → 回执(待验收)
                       └─ 若有 criteria 且自身不是复核单
                          → 平台自动建复核单 <task_id>-rv（同一 trace）
                             派给「与执行者不同且在线的实例」
                                  ├─ 复核 pass → 原单保持待验收，等签收
                                  └─ 复核 fail → 原单转验收驳回 + 理由 + 扣 retry
```

规则细节：

1. **复核者选择**：`payload.reviewer` 显式声明优先；否则取「`instance_id` ≠ 执行者、`online=true`、`in_flight` 最小」的实例。
2. **没有合格复核者**：不建复核单，任务标 `review_verdict=unreviewed`，note 里点明"缺复核者"。人仍可签收，但签收需显式 `force_accept=true`（留痕）。
3. **复核单本身**：`review_of` 非空 → 不再生成复核单（防递归）；回执落 `verdict` 后，复核单直接「验收通过」。
4. **结论落点**：`verdict.items` 的条数**必须等于** criteria 条数；不等即判 `fail`（标准没被逐条回答）；任一项 `ok=false` 即 `fail`。
5. **驳回**：`fail` 时把逐项理由拼进 `reject_reason`，走既有重派路径（`remaining_retry` 扣减，耗尽转执行失败）。

### 3.3 签收闸门

`accept_pending_tasks` 增加条件：只推 `status=待验收` 且 `review_verdict ∈ {pass, null}`（老单无标准，保持原行为）。`review_verdict=fail` 的单在驳回时就已离开待验收，不会被带过；`unreviewed` 的单需 `human_confirm_resp` 带 `force_accept=true` 才推。

### 3.4 防作弊（四条硬约束）

| 约束 | 实现位置 | 违反结果 |
| --- | --- | --- |
| 复核 instance ≠ 执行 instance | 建复核单前校验 | 不建单，任务标 unreviewed，note 告警 |
| 复核单不得再派生复核单 | `review_of` 非空即跳过 | 无 |
| 逐项必须答满 | 回执解析时条数比对 | 判 fail |
| 复核结论不得被静默改写 | 只写一次；二次回执走幂等拦截 | 409 |

### 3.5 接口面

**不加路径**。`TaskView` 增加 `review_of` / `review_verdict` / `review_items` 三个字段（字段不是路径，接口仍是 11 条）。

### 3.6 怎么证明它有用（三单实测，判据写死）

| 用例 | 构造 | 判据 |
| --- | --- | --- |
| 正例 | 执行者做对，复核 pass | 人签收后 `验收通过`，`review_verdict=pass`，`review_items` 条数 = criteria 条数 |
| 负例 A | criteria 3 条，执行者只交 2 条成果 | 复核 `fail`，原单自动「验收驳回」，`reject_reason` 里必须出现缺失项编号 |
| 负例 B | 把复核指派回执行者同实例 | 不建复核单，任务 `unreviewed`，看板可见告警 |

三条都成立才算这批发货；只有正例通过不算。

## 4. B32-2：插件沉淀

### 4.1 目录规范

```
plugins/<name>/
  PLUGIN.md      # 元数据（见下）
  SKILL.md       # 做法，给 Agent 读
  probes.py      # 可选：自带断言，喂给一级规则复核
  CHANGELOG.md   # 每个版本一行，改了什么
plugins/index.json   # 清单：name / latest / versions[] / review_state / granted_to[]
```

`PLUGIN.md` 必填字段：`name`、`version`（semver）、`owner`、`applies_to`（岗位或业务线）、`inputs`、`outputs`、`criteria_template`（默认验收标准）、`reviewer_hint`（建议复核者）。

### 4.2 审核与授权

- `scripts/plugin_review.py`：校验元数据齐全、版本递增、CHANGELOG 有对应条目、`probes.py` 可跑、`SKILL.md` 非空 → 通过则 `review_state: draft → reviewed`。
- 授权：`index.json` 的 `granted_to` 列 instance；派单带 `plugin` 字段时校验该实例已授权，未授权直接拒单（不建任务）。
- 撤权：从 `granted_to` 移除即可，下一单生效。

### 4.3 与 B32-1 的联动

派单带插件时，一级规则复核先跑 `plugins/<name>/probes.py`（机器、秒级）；过了再派生异构复核单（贵、慢）。两层都过才算"符合团队标准"。

## 6. 风险与取舍

1. **假 fail 拖慢交付**：复核模型弱于执行模型时会把对的判错。缓解——`force_accept` 人工覆盖必须留痕，且每单可查是谁覆盖的。
2. **任务量翻倍**：每个有标准的单多一条复核单，台账行数涨。台账不删行，接受。
3. **复核者被"喂结论"**：复核单里带执行者的 `self_check`，可能诱导复核者照抄。缓解——payload 里同时给原始产物引用（`artifacts`/`script`），并要求 evidence 字段必须引用产物路径。
4. **老单无标准**：不受影响，维持人签收。

## 7. 与 SoduWork 的差别（为什么只借不装）

| | 本平台（B32 之后） | SoduWork |

| 岗位 | instance 级路由 + 岗位章 | 角色/团队 |
