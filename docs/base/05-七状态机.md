# 05 · 七状态机

## 七个任务状态（中文，不可改）

`待拆解` → `待调度下发` → `执行中` → `待验收` → `验收通过` / `验收驳回` / `执行失败`

使用中文而非英文，是因为台账要给人看、要能直接对账；英文缩写会让人反复查表。

## 合法迁移表

| 从 | 到 | 触发报文 |
| --- | --- | --- |
| 待拆解 | 待调度下发 | Master 完成拆解（平台落库时置位） |
| 待调度下发 | 执行中 | `task_dispatch`（过闸门后） |
| 执行中 | 待验收 | `task_return` |
| 执行中 | 验收驳回 | `task_reject` |
| 执行中 | 执行失败 | `task_abort`／平台超时判定 |
| 待验收 | 验收通过 | Master 判过（平台记状态） |
| 待验收 | 验收驳回 | Master 判驳 |
| 验收驳回 | 待调度下发 | 重新派发（`remaining_retry` 减 1） |
| 验收驳回 | 执行失败 | 重试次数耗尽 / 主动中止 |

## 非法迁移（一律 409，且**不落任何状态**）

- `验收通过` → 任意状态（终态，回不去）
- `执行失败` → `执行中`（要重来就新建任务，不改历史）
- `待拆解` → `执行中`（跳过拆解与派发）
- `执行中` → `验收通过`（跳过验收）
- 任何状态 → 不存在状态（422/400）

## 平台层 pipeline 状态（5 值，与任务状态是两套）

`pending` / `running` / `success` / `aborted` / `failed`

| 值 | 含义 |
| --- | --- |
| pending | 已建流水线，尚未有任务进入执行 |
| running | 有任务在执行中 |
| success | 全部任务验收通过 |
| aborted | 人工中止 |
| failed | 熔断或关键任务失败 |

## sender 取值（5 值）

`master` / `dsh` / `workbuddy` / `codex` / `user`

## 三条实现约束

1. **数据库层用 CHECK 约束兜底**：`pipeline_ledger.overall_status` 限 5 值、`task_ledger.status` 限 7 个中文值、`sender` 限 5 值。代码写错也进不了库。
2. **状态迁移只在服务层做**（`dispatch.py`），仓储层只提供"按 id 改状态"，不做判断。
3. **状态只前进不改历史**：改状态是"更新当前状态字段"，历史过程留在 JSONL 归档里，不靠状态字段追溯。

## 为什么不用 8 个以上状态

状态越多，报文与代码的分支越难对齐。7 个已能覆盖：待处理、可派发、在干、等判、过、驳（可重试）、死。再加状态（如"暂停中"）会与 pipeline 的 `pause_flag` 语义重复——暂停属于流水线级，不是任务级。
