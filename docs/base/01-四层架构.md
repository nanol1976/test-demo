# 01 · 四层架构

平台分四层，每层只干一件事，**跨层直接调用视为越权**。

```
┌─────────────────────────────────────────────┐
│ 第四层  决策层  Master（智能体）               │
│ 拆解 / 派发 / 验收判定 / 审批决策              │
└───────────────────┬─────────────────────────┘
                    │ 只通过协议报文交互
┌───────────────────▼─────────────────────────┐
│ 第三层  执行层  Worker（workbuddy / codex / dsh）│
│ 接活 / 执行 / 心跳 / 回传 / 报错               │
└───────────────────┬─────────────────────────┘
                    │ 只通过协议报文交互
┌───────────────────▼─────────────────────────┐
│ 第二层  平台层  本工程                        │
│ 接入 / 队列 / 路由 / 台账 / 超时 / 熔断 / 前端  │
└───────────────────┬─────────────────────────┘
                    │
┌───────────────────▼─────────────────────────┐
│ 第一层  存储层  SQLite（可换 PG）+ JSONL 归档 │
└─────────────────────────────────────────────┘
```

## 各层职责与禁区

| 层 | 负责 | 明确不做 |
| --- | --- | --- |
| 决策层 Master | 需求拆解、任务下发、验收判定、高危审批 | 不直接写库、不绕过平台派活 |
| 执行层 Worker | 领任务、执行、回传结果、报错、心跳 | 不自己改别的任务状态、不碰台账 |
| 平台层（本工程） | 收报文、排队、路由、落台账、判超时/心跳/熔断、提供查询与界面 | 不做业务判断、不拆 DAG、不判验收、不删数据 |
| 存储层 | 持久化 | 不承载业务逻辑 |

## 三条硬边界

1. **平台不判断业务**。它只认协议字段和状态机，不理解"这件事做得好不好"。判验收是 Master 的事。
2. **Worker 不越权**。Worker 只能改自己 task_id 的任务状态，且必须走报文。
3. **台账不删**。任何层都不许删行；要"撤销"只能追加一条新报文并改状态。

## 为什么这么分

- 决策与基础设施解耦：换 Master 模型不改平台代码；换存储不改协议。
- 每层可替换：平台可换队列实现（进程内 → Redis），Master 可换 Codex/其他模型，Worker 可加新执行方。
- 故障可隔离：平台挂了 Worker 还在跑；Master 挂了任务停在"待调度下发"，不会丢。

## 与现成工具的关系

评估过 DolphinScheduler / Kestra / Dagu / HiClaw / Orloj / LangGraph：**没有一款能对齐本协议 v1.0**（它们要么绑 DAG 语义，要么无幂等归档契约，要么状态机不可定制）。所以自研平台层，但复用其思想：有界队列 + 回执、幂等键、熔断、暂停恢复。
