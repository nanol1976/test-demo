# 12 · 版本变更规范

## 什么时候必须升协议版本

| 变更 | 是否升版本 | 理由 |
| --- | --- | --- |
| 新增可选 payload 字段 | 不用（v1.0 兼容） | 老报文照旧能过 |
| 新增 msg_type | **升 v1.1** | 白名单变了，老实现会 400 |
| 改必带字段（增删改必填/类型） | **升 v1.1** | 老报文会 422 |
| 改状态机合法迁移 | **升 v1.1** | 老客户端的行为会被判非法 |
| 改语义（如超时判定的侧重点） | **升 v1.1** | 同样的报文结果不同 |
| 改字段长度上限 | **升 v1.1** | 原本能过的报文会被拒 |
| 纯内部重构、性能优化 | 不用 | 对外行为不变 |

## 变更流程（六步，缺一不可）

1. **写变更单**：改什么、为什么、影响谁（Master / Worker / 运维 / 前端）。
2. **改文档先于改代码**：`docs/base/` 里对应文件先更新（文档是口径来源）。
3. **改代码**：协议字段 → 模型/CHECK 约束 → 状态机 → handler → 接口。
4. **补/改断言**：`verify_bN.py` 必须覆盖新行为；**不许删掉旧断言来"让它绿"**。
5. **双端跑**：Windows + Mac 结果逐行一致，才算过。
6. **落验收单**：写进 `docs/NN-BatchN-验收单.md`，含真实终端输出、判定语义表、自测修缺陷、遗留。

## 版本号约定

- **协议版本**：`v1.0` → `v1.1`（报文里 `version` 字段）。加 `v2.0` 只在大改结构（如换状态模型）。
- **工程版本**：`app.main` 的 FastAPI `version` 字段；每次收口批 +1 小版本（0.1.0 → 0.2.0）。
- **批次标签**：git tag `batchN`。**每批一 tag**，出问题能回到干净状态。

## 不许做的事

1. 不许"先改代码后补文档"——文档滞后就没人信文档。
2. 不许为了让断言通过而放宽断言（例如把数量断言改成"大于 0"）。
3. 不许跳过双端一致就宣布完成——单端通过不算通过。
4. 不许在验收单里写"应该没问题"——只写实测输出。

## 回滚

- 代码回滚：`git reset --hard batchN`（每批有 tag，找得回来）。
- 数据回滚：**没有**。台账禁删，历史只能追加。所以**改协议前先备份库与归档目录**。
