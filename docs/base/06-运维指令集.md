# 06 · 运维指令集

平台只接受 3 条运维指令，通过 `POST /api/commands` 下发。**不接受其它指令**，未知指令一律 400。

## 三条指令

| 指令 | 作用 | 影响范围 | 是否改任务状态 |
| --- | --- | --- | --- |
| `master:pause` | 暂停该 trace | 只拦截**后续派发** | **不改**，任务现有状态原样保留 |
| `master:resume` | 恢复该 trace | 解除暂停 + **顺带复位熔断** | 不改 |
| `master:clear-breaker` | 仅复位熔断 | 不动暂停标记 | 不改 |

## 请求 / 响应

```json
POST /api/commands
{ "command": "master:pause", "trace_id": "t-001", "reason": "人工排查中" }
```

```json
200 OK
{ "trace_id": "t-001", "command": "master:pause", "paused": true, "breaker_open": false }
```

失败：
- 未知指令 → 400
- trace 不存在 → 404

## 为什么"resume 顺手复位熔断"

暂停与熔断都会拦派发。人按 resume 的心理预期是"让它继续跑"，如果只解暂停不解熔断，用户会发现"我恢复了但还是 409"，得再补一条指令。合并成一步更符合直觉。
如果只想解熔断、不想解暂停，用 `master:clear-breaker`。

## 暂停期间会发生什么

- 派发 → 409「流水线 X 处于暂停状态，需先 resume」
- **已经在执行的任务不受影响**（不会被打断）——暂停拦的是"新活"，不是"在干的活"
- 心跳、回传、归档照常受理

## 熔断期间会发生什么

- 派发 → 409「流水线 X 已熔断（连续失败任务数 N ≥ 阈值 M）」
- pipeline 已被置 `failed`
- 熔断状态**存在进程内存**，**重启即复位**（这是已知遗留，持久化需加字段+迁移，暂不做）
- 同 trace 的失败任务计数是**累计值**，不是"连续"——文档口径以"失败任务数 ≥ 阈值"为准（命名沿用 `failure_threshold`）

## 运维操作速查

| 想干什么 | 指令 |
| --- | --- |
| 临时停一条流水线 | `master:pause` |
| 继续 | `master:resume` |
| 熔断了但不该停 | `master:clear-breaker` |
| 全部任务重来 | 新建 trace（**不是**改老台账） |
| 看整体情况 | `GET /api/pipelines` |
| 看一条流水线 | `GET /api/pipelines/{trace_id}` |
| 导出台账快照 | `GET /api/export/{trace_id}?format=json|csv` |
| 查归档落盘情况 | `GET /api/archive/{trace_id}` |

## 界面入口

Batch5 的看板已把三条指令做成按钮（详情面板的「暂停派发 / 恢复派发 / 复位熔断」），不用记 curl。
